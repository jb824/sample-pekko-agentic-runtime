# dev_ses2_06052026: Consumer Infrastructure Review Findings

## Findings

### 1. High: Timed-Out Consumer Invocations Can Continue Running Concurrently With Later Events

**File:** `runtime/src/main/java/com/example/agent/runtime/consumer/ConsumerWorkerActor.java`
**Lines:** `129-144`

`onProcessingTimeout` clears `inFlight` and immediately drains the next event, but the original `CompletableFuture` is not cancelled/interrupted. That means a slow `onAgentCompleted` can keep running on the consumer executor while the same `AgentConsumer` starts processing the next event.

**Scenario:** A consumer writes to an audit/evaluation store after a slow LLM call. If it times out, request-2 can start while request-1 is still mutating state. This violates the "one event handling transaction at a time per logical consumer" model and makes idempotency harder because late side effects still happen.

**Suggested fix:** Either keep the worker busy until the original future completes, treating timeout as a failure but not starting the next event, or make cancellation explicit with a cancellable/interruptible task contract and document that timed-out handlers must tolerate interruption.

---

### 2. Medium: Validation Failures Bypass the Consumer Pipeline Entirely

**File:** `runtime/src/main/java/com/example/agent/api/AgentRuntime.java`
**Lines:** `71-76`

`AgentRuntime.run(...)` returns validation failures directly as completed futures before invoking the actor runtime. Since consumers are only dispatched from `DefaultAgentSystemExecutorActor`, registered consumers never see unsupported task or invalid task results.

**Scenario:** An audit/metrics consumer expects one terminal event per `AgentRuntime.run(...)`. Invalid requests return `FAILED_SYSTEM` to the caller but produce no `AgentCompletedEvent`, so failure counts and audit trails are incomplete.

**Suggested fix:** Keep a reference to the consumer registry or a small dispatcher service in `AgentRuntime` and dispatch validation failures before returning the completed future. Alternatively document that consumers only observe requests accepted by `GatewayActor`.

---

### 3. Medium: `ConsumerWorkerActor` Uses an Unbounded Internal Pending Queue

**File:** `runtime/src/main/java/com/example/agent/runtime/consumer/ConsumerWorkerActor.java`
**Lines:** `21`, `75-78`

While a consumer is in-flight, the actor keeps accepting all `Process` messages and moves them into an unbounded `ArrayDeque`. That means the actor mailbox is not the actual backpressure boundary; slow or stuck consumers can accumulate unbounded heap in `pending`.

**Scenario:** High request throughput with one slow audit/evaluation consumer. The registry forwards every event, the worker drains them into `pending`, and memory grows until the consumer catches up or the process runs out of heap.

**Suggested fix:** Use a bounded queue/stash with a configured maximum and log/drop/fail when full, or keep events in the actor mailbox by switching behavior and only accepting completion/timeout while busy.

---

### 4. Low: Exact 30s Consumer Override Is Ignored When Config Differs

**File:** `runtime/src/main/java/com/example/agent/runtime/consumer/ConsumerWorkerActor.java`
**Lines:** `148-153`

The worker treats any `consumer.processingTimeout()` equal to `AgentConsumer.DEFAULT_PROCESSING_TIMEOUT` as "use runtime default config." If a consumer explicitly returns `Duration.ofSeconds(30)` while `CONSUMER_PROCESSING_TIMEOUT_SECONDS=5`, the consumer cannot force 30 seconds.

**Suggested fix:** Avoid value-based detection of "not overridden." Either always use `consumer.processingTimeout()` or add an explicit nullable/internal method for default resolution.

---

The implementation otherwise keeps the runtime infrastructure-only: evaluator/reviewer logic is outside `runtime`, and the core SPI (`AgentConsumer`, `ConsumerEffect`, `AgentCompletedEvent`) is small and appropriate.
