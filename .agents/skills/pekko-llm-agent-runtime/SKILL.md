# Skill: Build a Pekko LLM Agent Runtime

Use this skill when building or extending a local JVM agent runtime where **Apache Pekko Typed** owns orchestration and LLM/tool integrations sit behind explicit actor boundaries.

The runtime should prove this shape before adding distributed features:

```text
Main / external adapter
  -> GatewayActor
      -> ResearchWorkflowActor or PlannerExecutorWorkflowActor
          -> LlmWorkerActor
          -> ToolRegistryActor
              -> TimeToolActor / WebSearchToolActor / ArxivSearchToolActor
```

## Current Stack

- Java 21
- Gradle Kotlin DSL where generated by `gradle init`
- Apache Pekko Typed
- LangChain4j for Ollama `ChatModel`
- Direct Java `HttpClient` adapter for vLLM OpenAI-compatible endpoints
- Ollama for easy local model runs
- vLLM for concurrency and throughput experiments
- Logback for local logs

Pin dependency versions. Pekko artifacts require the Scala suffix, for example `_2.13`.

## Architecture Rules

Pekko owns orchestration. Do not hide workflow/tool execution inside a LangChain4j agent loop.

Use explicit actors and protocols:

```text
GatewayActor
  - accepts requests
  - validates/policy-gates requests
  - creates one workflow actor per request
  - does not call the LLM or tools directly

WorkflowActor
  - owns request state
  - tracks correlation IDs
  - chooses bounded LLM/tool steps
  - returns one AgentResponse
  - stops after completion/failure/timeout

LlmWorkerActor
  - owns model client access
  - runs blocking calls on a bounded dedicated executor
  - returns failures as messages

ToolRegistryActor
  - routes approved tool calls to tool actors
  - rejects unknown tools

ToolActor
  - performs one deterministic bounded capability
  - returns ToolResult
```

Everything crossing actor boundaries should be an immutable Java record.

Minimum protocols:

```java
record AgentRequest(String requestId, String input) {}
record AgentResponse(String requestId, String output, Throwable error) {}
record LlmAsk(String requestId, String prompt, ActorRef<LlmResponse> replyTo) {}
record ToolInvoke(String requestId, String toolName, Map<String, String> arguments, ActorRef<ToolResult> replyTo) {}
```

Use correlation IDs:

```text
<requestId>:plan
<requestId>:tool:time.now
<requestId>:tool:web.search
<requestId>:tool:arxiv.search
<requestId>:execute
```

## Implementation Order

1. Create the Gradle Java application and wrapper.
2. Add Pekko Typed, Pekko SLF4J, LangChain4j Ollama, Jackson, Logback, and JUnit.
3. Add `application.conf` with local actor provider.
4. Implement `AppConfig` from environment variables.
5. Implement `LlmProtocol`, `LlmWorkerActor`, and model factories.
6. Implement `ResearchWorkflowActor`.
7. Implement `GatewayActor`.
8. Implement `PlannerExecutorWorkflowActor`.
9. Add `ToolProtocol`, `ToolRegistryActor`, and deterministic `TimeToolActor`.
10. Add `web.search` and `arxiv.search` tool actors.
11. Add tool-selection policy.
12. Add bounds and metrics.
13. Add vLLM concurrency script.

Avoid adding cluster sharding, persistence, RAG, streaming, Kubernetes, or tenant isolation until the single-node actor flow works.

## LLM Worker Pattern

Never call `model.chat(...)` directly on the actor dispatcher.

Use:

```text
actor message
  -> CompletableFuture on bounded ExecutorService
  -> pipeToSelf / adapter result
  -> reply as message
```

Use a bounded executor, not `newFixedThreadPool` with an unbounded queue:

```java
new ThreadPoolExecutor(
    llmThreads,
    llmThreads,
    0L,
    TimeUnit.MILLISECONDS,
    new ArrayBlockingQueue<>(llmQueueSize),
    namedThreadFactory("llm-worker")
)
```

Catch `RejectedExecutionException` and return it as an LLM response error. Executor saturation is a runtime signal, not an actor crash.

Shutdown the executor after the actor system terminates. Do not block an actor message handler waiting for executor shutdown.

## Ollama Notes

LangChain4j `OllamaChatModel` uses the base URL without `/api`:

```text
http://localhost:11434
```

Ollama failures to expect:

- model not pulled
- model name mismatch
- local GPU/VRAM OOM
- slow first token after model load

Treat these as LLM response errors, not thrown cross-actor failures.

## vLLM Notes

vLLM serves an OpenAI-compatible API:

```text
http://localhost:8000/v1
```

Always check the exact served model ID:

```bash
curl http://localhost:8000/v1/models
```

Use that exact ID as `VLLM_MODEL`. A local alias like `gemma-3-1b-it` may fail when the server exposes `google/gemma-3-1b-it`.

Model/API guidance:

```text
*-pt base/pretrained model -> VLLM_API_TYPE=completion
*-it or instruct/chat model -> VLLM_API_TYPE=chat
```

Base/pretrained models often produce poor instruction-following output. Prefer instruct/chat models for workflow tests.

If vLLM reports missing request body from Java clients, force HTTP/1.1 and send explicit JSON with `Content-Type: application/json`. In this project, a small direct Java `HttpClient` adapter was more reliable than a generic OpenAI client.

For tiny 1B models:

- keep planner output format very small
- include a system prompt in chat mode
- set `VLLM_MAX_TOKENS`
- expect weak factual quality
- judge actor/runtime behavior separately from answer quality

## Planner/Executor Workflow

For tiny models, do not ask for complex JSON. Use a small structured format:

```text
PLAN:
1. ...
2. ...
3. ...
TOOLS: time.now, web.search, arxiv.search
```

Then workflow code should:

1. Parse the `TOOLS:` line.
2. Fall back to simple heuristics if the model omits tools.
3. Intersect requested tools with `AGENT_TOOLS`.
4. Limit count with `AGENT_MAX_TOOLS`.
5. Execute approved tools.
6. Pass tool context into the executor prompt.

Do not let LLM output directly control actor spawning or arbitrary tool execution.

## Tool Policy

Tools are runtime capabilities, not LLM-owned functions.

First tool set:

```text
time.now      -> deterministic current time
web.search    -> DuckDuckGo Instant Answer JSON
arxiv.search  -> arXiv API Atom XML
```

The registry should reject unknown tools. The workflow should handle individual tool failures as context unless the tool is mandatory.

Recommended environment:

```bash
AGENT_TOOLS=time.now,web.search,arxiv.search
AGENT_MAX_TOOLS=2
TOOL_TIMEOUT_SECONDS=30
WORKFLOW_TIMEOUT_SECONDS=180
```

Search tool cautions:

- keep result count small
- cap query length
- do not log sensitive raw user data by default
- web search results may be absent or low quality
- arXiv API is slower and returns XML; parse with secure XML settings

## Metrics

Add lightweight stdout metrics early:

```text
METRIC request_id=<id> success=<true|false> latency_ms=<n>
METRIC summary requests=<n> success=<n> failure=<n> total_ms=<n> workflow=<mode> backend=<backend> tools=<tools>
```

Concurrency scripts can parse the summary:

```text
BENCH concurrency=8 requests=8 success=8 failure=0 total_ms=...
```

For deeper work, add:

- LLM latency per step
- tool latency per tool
- queue rejection count
- timeout count
- prompt length
- response length

## Bounds

Bound everything before serious concurrency tests:

```text
LLM_THREADS
LLM_QUEUE_SIZE
LLM_TIMEOUT_SECONDS
AGENT_REQUESTS
AGENT_MAX_TOOLS
TOOL_TIMEOUT_SECONDS
WORKFLOW_TIMEOUT_SECONDS
VLLM_MAX_TOKENS
```

Timeout policy:

- LLM timeout belongs in the model client request.
- Tool timeout belongs in the workflow, not only the HTTP client.
- Workflow timeout should fail the request and stop the workflow actor.
- Late tool responses after timeout should be ignored.

## Concurrency Script

Add a script such as:

```bash
scripts/test-vllm-concurrency.sh
```

Recommended behavior:

1. Check `${VLLM_BASE_URL}/models`.
2. Print model, API type, token budget, tools, concurrency levels.
3. Run `./gradlew --quiet run` with `LLM_BACKEND=vllm`.
4. Sweep `CONCURRENCY_LEVELS`.
5. Print app output and a compact `BENCH` line.

Example:

```bash
VLLM_MODEL=google/gemma-3-1b-it \
VLLM_API_TYPE=chat \
VLLM_MAX_TOKENS=512 \
AGENT_PROMPT='Research recent Apache Pekko typed actor best practices and include related arXiv context if available.' \
AGENT_WORKFLOW=planner-executor \
AGENT_TOOLS=time.now,web.search,arxiv.search \
AGENT_MAX_TOOLS=2 \
CONCURRENCY_LEVELS='1 2 4 8' \
LLM_THREADS=8 \
./scripts/test-vllm-concurrency.sh
```

## DO NOTs

Do not:

- create one `ActorSystem` per request
- block actor handlers with LLM or HTTP calls
- use unbounded executor queues for LLM calls
- let LLM output directly spawn actors or run arbitrary tools
- treat tool failures as Java exceptions crossing actor boundaries
- add cluster sharding before proving single-node boundaries
- add RAG/vector DB before basic LLM/tool workflows work
- stream every token as an actor message
- log sensitive prompts/tool queries by default
- rely on tiny model answer quality to judge actor runtime correctness
- use chat completions with base `*-pt` models unless vLLM has a chat template
- assume vLLM model name from local shorthand; query `/v1/models`

## Validation Checklist

Run at least:

```bash
./gradlew compileJava
./gradlew test
./gradlew run
```

For vLLM:

```bash
curl http://localhost:8000/v1/models
VLLM_MODEL=<exact-id> CONCURRENCY_LEVELS='1' ./scripts/test-vllm-concurrency.sh
```

A successful runtime test should show:

- Pekko actor system starts
- request is submitted through `GatewayActor`
- workflow actor sends planner LLM call
- selected tools are policy-gated
- tool actors return results or bounded failures
- executor LLM call receives tool context
- one final `AgentResponse` per request
- `METRIC summary` appears
- coordinated shutdown completes

## When to Add Tests

For a raw MVP, live local runs are acceptable. Once tool policy or bounds exist, add actor tests with fake LLM/tool actors.

Test these first:

- planner -> selected tool -> executor success
- unknown tool rejected
- tool timeout proceeds or fails as designed
- LLM executor saturation returns response error
- concurrent workflows all complete

Do not let the lack of fake tests block early prototyping, but do not trust concurrency changes without some deterministic tests before productionizing.
